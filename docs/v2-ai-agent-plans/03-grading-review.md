# 阶段 3：评分复核闭环与掌握度落地

## 阶段定位

在不引入 LangGraph 的前提下，建立低置信度评分、申诉、人工复核和掌握度更新闭环，供普通做题与后续状态机共同复用。

- 主计划依据：2.4、3.1.3、3.4.1、3.4.2、3.6、第 4 节、阶段 3。
- 前置依赖：阶段 0A、0B 审核通过。
- 后继解锁：阶段 4、5。

## 执行范围

1. migration：
   - `answer.version` 默认 0，每次成功提交原子加一。
   - 完整创建 `ai_grading_reviews`，含提交快照、fingerprint、answer version、状态与审核字段。
2. 抽取可复用评分链：
   - 代码题用 LCEL + zod。
   - 保持现有 functional/quality/hint deduction 语义。
   - 选择题继续规则判定，AI 只解释。
3. 实现低置信度/规则冲突检测并创建复核单。
4. 实现管理员复核接口与最小可用复核队列 UI；实现用户申诉入口和状态反馈。
5. 人工结论生效后，按 3.4.2 事件矩阵写入 `mastery_level`。
6. 同一提交幂等、重复审核幂等、旧提交复核保护。
7. 复用提示服务写入的数据库状态，提交接口不信任客户端 `hint_level_used`。
8. 选择题和代码题均按 `Math.max(existingAnswer.score, score)` 保留最佳分。

## 掌握度红线

- 自动事件可以提升或保持掌握度。
- 任何下降或“未掌握”结论必须经过人工复核。
- 待审状态不得提前修改掌握度。
- 旧 `answer_version` 的复核结论只能留审计，不能覆盖新提交状态。
- 事件矩阵之外的事件不得写入。

## 禁止事项

- 不给选择题增加无意义的 AI 多维评分。
- 不实现新的题型或真沙箱。
- 不把普通做题路径改成 LangGraph。
- 不信任客户端提交的提示级别、分数或置信度。
- 不用可变的 `answer` 行代替复核快照。

## 必须验证

- 选择题行为与 V1 一致；代码题结构化字段齐全。
- 低置信度触发 → 待审 → 维持/改判 → 掌握度更新全链路可复现。
- 用户申诉能进入同一可追溯复核体系。
- 同一 fingerprint 重复触发只创建一张对应复核单。
- 重复审核不重复改分、改掌握度或加积分。
- 提交 A 待审、提交 B 更新后再处理 A，A 被标 stale/仅审计。
- 评分合并和掌握度纯函数 vitest 通过。
- 做题手工回归覆盖选择题、代码题、提示扣分、AI 失败降级。
- 至少 30 条分层代码题样本中，人工通过结论一致率 ≥ 90%，平均绝对误差 ≤ 10。

## 交付物

- migration、评分链、复核/申诉 service 与 route。
- 最小必要的管理员复核和用户申诉界面。
- 单元测试、状态流转与过期复核故障用例。
- 评分评测集、逐条结果和聚合报告。
- 主流程回归记录。

## 审核门禁

- migration 唯一键和索引能支撑幂等与待审队列。
- `answer.version` 与 fingerprint 双重保护生效。
- 无未经人工复核的降分或未掌握写入。
- 现有做题链路和最佳分规则无回归。
- 评分质量门槛按正确/错误/边界样本分层报告。
