# CodeStory V2.0 AI 阶段任务书

本目录把 [`CodeStory_V2.0_AI增强执行计划.md`](../CodeStory_V2.0_AI增强执行计划.md) 拆成可直接派发给执行 agent 的阶段任务书。主计划仍是需求与技术决策的唯一事实源；阶段任务书只负责界定执行边界、依赖、交付物和审核门禁。

## 1. 使用方式

每次只把一个阶段任务书连同仓库根目录的 `AGENTS.md` 交给执行 agent。执行 agent 不得自行宣布阶段完成，只能提交“待审核”交接报告；审核者检查代码、迁移、测试与手工证据后给出：

- `通过`：本阶段门禁全部满足，可以解锁后继阶段。
- `条件通过`：代码可合并，但有明确记录、且不阻塞后继开发的环境验证尚待补跑。
- `退回`：存在范围偏移、关键测试缺失、数据一致性风险或回归。

执行 agent 的最终交接必须包含：

1. 改动摘要与逐文件清单。
2. 数据库迁移、环境变量、依赖和接口协议变更。
3. 实际执行的命令及结果，不得只写“已测试”。
4. 手工回归步骤、输入、预期结果和实际结果。
5. 未验证项、阻塞项、已知风险和对主计划的任何偏差。
6. `git status --short` 与本阶段相关 diff 概述。

默认不要让执行 agent 创建提交；先保留工作区 diff 供审核。需要提交时再遵循仓库的 Conventional Commit 约定。

当前仓库已有未提交工作。执行 agent 开始前必须运行 `git status --short`、识别并保留既有改动；不得使用 `git reset --hard`、`git checkout --` 或清理命令覆盖其他人的工作。

## 3. 推荐执行波次

```text
波次 A：0A 初审 ── 0B ── 0A 最终审核
                         ├── 波次 B1：阶段 1 ── 阶段 2 ── 阶段 4
                         └── 波次 B2：阶段 3 ─────────┬── 阶段 5
                                                     └── 阶段 4
波次 C：阶段 4 + 阶段 5 均通过 ── 阶段 6
发布门禁：0C 完成 + 阶段 6 发布结论
```

如果多个 agent 共享同一个工作目录，不要并行写代码。阶段 1 与阶段 3、阶段 4 与阶段 5 只有在使用隔离分支或独立 worktree、并约定文件所有权时才适合并行；否则按顺序派发，避免彼此覆盖。

## 4. 全阶段共同约束

- 先阅读主计划的第 2～4 节、自己阶段对应章节、第 5.1/5.2 节。
- 只做当前阶段列出的范围；发现前置问题先报告，不顺手重构。
- 保持 `POST /ai/chat/stream` 的既有自由对话流程不变；RAG 只进入上下文装配层。
- 选择题继续规则判定；代码题沿用 AI 评阅边界。AI 不得未经人工复核下调既有成绩或判定未掌握。
- AI 生成内容先为 `draft`，审核为 `approved` 后才对学习端可见。
- PostgreSQL 业务数据是事实源；向量、checkpoint 投影和模型生成内容必须可重建或可补偿。
- 新增管理接口统一使用现有 `authMiddleware + requireAdmin`，并做资源归属检查。
- 不记录 Token、验证码、联系方式、完整敏感 Prompt 或生产凭据。
- 可见前端改动必须遵循 `docs/CodeStory_前端设计规范.md` 并复用现有后台/小节组件。
- 不实现真沙箱、`fill`/`judge`、消息队列、完整 E2E、短 ID 全局重构或 V2.1 业务模块。
- 不提交 `.env`、dump、backup、uploads、生产数据、生成构建产物。

## 5. 统一审核门禁

每阶段至少执行与改动匹配的检查：

```powershell
cd backend
pnpm run build
pnpm run test

cd ..\frontend
pnpm run check
pnpm run build
```

若阶段未改前端，可以不跑前端 build，但必须说明理由。涉及数据库的阶段还须提供 migration 状态、独立测试库结果和回滚/补偿证据；涉及外部模型的阶段须区分“固定输入 Schema 测试”和“真实端点可靠性实测”。

审核者重点检查：

- 是否只改本阶段范围，是否覆盖或夹带既有工作区改动。
- migration 是否向前兼容、可在空库和现有库执行，默认值是否安全。
- 权限、资源归属、并发、幂等、失败降级和敏感信息处理是否成立。
- 测试是否真正覆盖主计划指定的失败模式，而非只走成功路径。
- 完成标准是否有可重复证据；未达到质量门槛时是否保持功能开关关闭。

